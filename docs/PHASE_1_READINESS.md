# Vivi Phase 1 Readiness and Audit

Status: implemented and reviewed; final Phase 1 verification draft

## Audit summary

Phase 0 provides a useful scope and direction, but it is a planning baseline rather than a validated architecture. The remote repository and Git state are now confirmed, and the README has been corrected to match the pushed repository.

## Issues discovered

### Contradictions and stale assumptions

- The original README claimed that the remote was empty and the local workspace had no history after the repository was initialized and pushed.
- Phase 0 status remained "in progress" after completion.
- The database design was partially implementation-specific: every private record did not always need a direct `user_id` if access is derived through a kit or class, but authorization must still be explicit and testable.
- "Every private record derives access" is too broad as a schema rule; a helper/segment should inherit ownership through a join and must enforce that relationship at write and read time.
- The roadmap listed 11 phases but no exact exit criteria for Phases 6–11.
- The free-infrastructure document named Qwen3/Qwen2.5 candidates but did not record quantization, memory, context, or benchmark criteria.
- The PRD allowed "catalog" in initial scope while the feature inventory described it as future.

### Missing requirements

- No formal data retention or account deletion schedule.
- No job status payload or idempotency specification.
- No migration rollback policy.
- No health/readiness endpoint specification.
- No request correlation or structured logging requirement.
- No content-size limits by material type.
- No exact supported browser/runtime targets.
- No explicit backup and restore verification procedure.
- No license inventory format for dependencies and model artifacts.
- No hardware benchmark acceptance threshold.

### Security weaknesses

- The existing security document says "signed or server-resolved file access" but does not require short-lived file URLs or authorization on every file request.
- CSRF strategy was named but not specified.
- Session revocation and session fixation handling need an explicit design.
- Rate limiting storage is not specified and must not introduce Redis in Phase 1 unless required.
- Upload antivirus scanning is not feasible for a free MVP, so file parsing and sandboxing limitations must be documented rather than implied.
- Account deletion should distinguish soft deactivation, asynchronous cleanup, and verified backup retention.

### Hardware and cost risks

- 16 GB RAM can support one small generation model and one small embedding model with CPU, but simultaneous GPU loading of PostgreSQL, the frontend, Ollama, and a 4B model may exhaust memory.
- Docker Desktop licensing and resource behavior must be reviewed separately on Windows.
- Ollama, Qwen, pgvector, PostgreSQL, Caddy, and GitHub Actions must remain optional or free under the selected deployment path.
- Domain names, TLS infrastructure, internet, electricity, physical storage, backup media, hardware, and support time remain real costs.

### Dependency and license review

- Ollama is MIT licensed.
- pgvector uses a permissive PostgreSQL-style license.
- BGE-M3 is MIT licensed.
- Multilingual-E5-base is MIT licensed.
- Qwen2.5-1.5B-Instruct is Apache-2.0 licensed.
- Qwen3-4B-Instruct-2507 is Apache-2.0 licensed.
- Final dependency licenses must be regenerated by the package manager at implementation time; model licenses must be checked against the exact artifact revision.

## Recommended Phase 1 architecture

```text
frontend/
  app/
  components/
  features/
  lib/

backend/
  app/
    api/
    core/
    models/
    schemas/
    repositories/
    services/
    ai/
  migrations/
  tests/
  worker/

infrastructure/
  docker/
  caddy/

docs/
scripts/
.github/
```

Keep the structure minimal: no domain folders or abstractions until an implementation need is measurable.

### Frontend baseline

- Next.js App Router
- React and TypeScript
- Tailwind CSS
- shadcn/ui and Radix UI only if components are needed
- TanStack Query, React Hook Form, Zod, and Lucide are candidates but should not be installed in Phase 1 unless a foundation endpoint requires them
- `/api/v1/health/live` and `/api/v1/health/ready` developer smoke views are sufficient for Phase 1

### Backend baseline

- FastAPI
- Pydantic
- SQLAlchemy 2.x
- Alembic
- HTTPX only if integration tests require it
- Argon2 is authentication-ready but registration/login code is not required in Phase 1
- Python 3.12 minimum, with 3.12/3.13 compatibility and 3.14 blocked until dependency support is verified

### Database baseline

- PostgreSQL 16 or 17
- pgvector only when the initial migration explicitly requires it
- SQLAlchemy migrations through Alembic
- A baseline migration that creates required extension capability only if the runtime image provides the extension
- PostgreSQL-backed job tables deferred unless Phase 1 foundation work explicitly proves no separate queue package is needed

### AI baseline

Do not install Ollama or model weights in Phase 1. Implement no Ollama call. A provider protocol and explicit unavailable-state contract may be documented but no model-specific code is required.

## Development environment

- pnpm for frontend
- uv for backend
- Docker Compose for PostgreSQL and optional Caddy paths only after Docker approval
- Native PostgreSQL is an acceptable alternative if Docker cannot be used
- `.env.example` documents non-secret sample values
- `.env`, databases, uploads, backups, and model caches remain ignored

## Configuration

Minimum environment groups:

- `APP_ENV`, `APP_NAME`
- `PUBLIC_APP_URL`
- `DATABASE_URL`
- `SESSION_SECRET`
- `SECURE_COOKIES`
- `STORAGE_ROOT`
- `AI_PROVIDER`, `OLLAMA_BASE_URL`, `OLLAMA_MODEL`
- `LOG_LEVEL`
- `CORS_ORIGINS`
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`

No default secret is accepted in a non-local environment. Password and session secrets must fail fast when missing or too short.

## API conventions

- JSON REST routes below `/api/v1`
- Pydantic 2 request and response schemas
- RFC-style stable error JSON containing `code`, `message`, `request_id`, and optional field details
- No stack traces or secrets in responses
- HTTP 422 for validation, 401 for missing auth, 403 for authorization failures, 404 for hidden private records
- Cursor or keyset pagination for future collections
- Health endpoints are public and reveal no sensitive configuration

## Logging and errors

- Structured JSON in production, readable development output
- Correlation/request IDs in every response and log entry
- Central exception handlers
- Safe logs only: route, status, duration, request ID, and safe error code
- No prompt text, document text, passwords, cookies, tokens, or SQL bind values

## Security baseline

- Ownership checks are required in every protected service/repository operation
- Secrets only in environment variables or a future secret store
- Argon2id dependency is deferred until authentication implementation
- Session cookie fields: HttpOnly, Secure outside local HTTP, SameSite=Lax, short/moderate lifetime, server-side revocation
- CSRF must use an origin check plus an anti-CSRF mechanism for mutation routes
- Security headers through Next.js/Caddy/FastAPI
- Upload validation remains a Phase 4 concern
- Add a single secret/credential pre-commit review gate before each push

## Phase 1 implementation sequence

1. Confirm runtime and dependency compatibility.
2. Establish repository structure and configuration.
3. Create backend settings and application factory.
4. Add PostgreSQL/Alembic baseline.
5. Add health endpoints and readiness checks.
6. Add middleware, error envelope, logging, and request IDs.
7. Add provider/storage contracts and safe unavailable behavior.
8. Establish frontend shell and design tokens.
9. Add focused backend and frontend tests.
10. Run build, migration, lint, format, and test verification.
11. Perform documentation and secret review.
12. Stop for approval before authentication or feature implementation.

## Acceptance criteria

- Frontend installs from lockfile and passes type checking/build.
- Backend installs in an isolated uv environment.
- Backend starts and `/api/v1/health/live` succeeds.
- Readiness correctly fails when PostgreSQL is unavailable and succeeds when it is ready.
- Alembic upgrade and downgrade smoke tests succeed against PostgreSQL.
- Central errors return the documented envelope.
- Logs contain no credentials or document/model payloads.
- Missing required secrets fail startup with an actionable local error.
- Frontend and backend test suites pass.
- No paid service or paid API is required.
- No Docker or Ollama installation has occurred unless explicitly approved in this phase.
- Documentation accurately distinguishes implemented and planned behavior.
- Repository diff contains no secrets or generated files.
